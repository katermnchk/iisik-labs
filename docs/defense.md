# Защита лабораторной работы 3

## Короткий рассказ на 2-3 минуты

В лабораторной работе я реализовала базовую структуру системы управления туристическими поездками для варианта 20. Проект состоит из GraphQL API и шести сервисов: пользователей, туров, бронирований, платежей, уведомлений и аналитики. Для каждого внутреннего сервиса подключена отдельная база PostgreSQL. Миграции Flyway создают таблицы и добавляют начальные данные.

В каждом сервисе есть модели таблиц, репозитории и методы чтения. Модели БД наружу не передаются: сервис возвращает DTO. Связи с другим сервисом хранятся как идентификаторы. Например, Booking хранит scheduleId и снимок цены, а не JPA-ссылку на расписание из чужой базы.

Внешний API реализован на GraphQL. Есть восемь Query: текущий пользователь, список туров, один тур, одна бронь, мои брони, уведомления, направления и аналитика. API умеет получать вложенные данные: у тура есть выезды, размещение и транспорт; у брони - список попыток оплаты. Фильтры по дате и цене относятся к одному выезду. Деньги хранятся в копейках, чтобы избежать ошибок округления.

GraphQL обращается к интерфейсам клиентов. Сейчас подключены mock-реализации с данными JSON. Реальных gRPC-вызовов нет, это условие ЛР3. При этом внутренние сервисы отдельно запускаются и читают настоящие базы. Поэтому изменение PostgreSQL пока не меняет ответ GraphQL. В следующих работах mock-клиент можно заменить сетевым без изменения обработчиков Query.

Учтены замечания предыдущих работ: описано создание профиля сотрудника при смене роли, дополнены protobuf-контракты, согласованы технические таблицы, события и enum. В аналитике продажа и возврат одного платежа хранятся отдельными фактами. Контракты записи и Kafka пока являются спецификацией, а не работающими функциями.

Я проверила сборку, автоматические тесты, ответы всех шести сервисов и работу GraphQL после отключения сервисов. Отдельно проверены чужая бронь, закрытая аналитика, неизвестный объект, фильтры, страницы и суммы продаж/возвратов.

## Вопросы и ответы

**Что такое GraphQL?** Язык запросов и правила выполнения API. Клиент выбирает нужные поля, сервер проверяет их по схеме и возвращает выбранную структуру.

**Чем Query отличается от Mutation?** Query читает данные. Mutation предназначен для изменения. Здесь активны только Query по заданию.

**Что такое schema и resolver?** Schema описывает допустимые типы и операции. Resolver - обработчик, который получает значение поля. В проекте @QueryMapping связывает методы контроллера с полями Query.

**Что обозначает !?** Значение не может быть null. [Payment!]! - список не null и элементы не null, но пустой список допустим.

**Почему объект отсутствует с HTTP 200?** HTTP-запрос принят и GraphQL выполнялся. Ошибка конкретного поля находится в errors, а nullable объект равен null. Для отсутствующего токена фильтр возвращает HTTP 401 ещё до выполнения.

**Что такое mock?** Учебная реализация интерфейса, возвращающая подготовленные данные. Здесь это mock всей стороны сервиса, а не подмена PostgreSQL: собственные БД проверяются отдельно.

**Зачем интерфейсы клиентов?** Слой Query не зависит от способа получения данных. Позже можно добавить gRPC-реализацию того же интерфейса.

**Что такое DTO?** Объект передачи данных. Он содержит нужные значения, не механизм хранения JPA. GraphQL схема определяет, какие поля DTO доступны клиенту; лишние поля и пароль в ответ не попадают.

**Чем Entity отличается от DTO?** Entity соответствует таблице и используется JPA. DTO передаётся между слоями и клиентами; не содержит JPA-аннотаций.

**Зачем Repository и Service?** Repository читает БД. Service собирает связанные данные и применяет правила. Controller принимает запрос и передаёт его сервису.

**Почему шесть БД?** Каждый сервис отвечает за свои данные. Он не меняет чужие таблицы. Можно развивать схему каждого сервиса отдельно.

**Как связывать объекты разных БД без FK?** Через UUID и сервисные контракты. Booking хранит snapshot выезда и цены, чтобы изменение тура не переписывало уже оформленную бронь.

**Что такое Flyway?** Инструмент последовательного применения SQL-миграций. Уже применённые V1/V2 не переписываются; новое изменение добавляется следующим файлом.

**Что такое gRPC и protobuf?** gRPC - способ удалённого вызова метода сервиса. Protobuf описывает сообщения, поля и их номера. Здесь есть исправленный .proto, но реальные вызовы не запускаются.

**Что такое producer, consumer и broker?** Producer публикует событие; broker хранит и передаёт сообщения; consumer читает и обрабатывает их. В будущей системе Payment публикует PaymentSucceeded, Analytics и Notification его обрабатывают. Kafka в ЛР3 не используется.

**Зачем outbox_events?** Чтобы записать изменение и событие одной транзакцией в одной БД. Отдельный процесс позднее отправит событие. Пока таблица только подготовлена.

**Зачем processed_events?** Чтобы повтор одного eventId не создавал второй факт или уведомление. Запись и изменение данных должны выполняться одной транзакцией.

**Почему sales_facts не имеет payment_id как PK?** Один платёж создаёт продажу и возврат, иногда несколько частичных возвратов. У факта свой fact_id, а операция имеет source_operation_id и уникальную пару с fact_type.

**Откуда у Payment scheduleId/directionId?** Из GetPaymentContext Booking Service. Booking раньше получил их от ReserveSeats Tour Service. Payment сохраняет значения у себя. Сейчас это явно описанная будущая цепочка.

**Как появляется Employee profile?** Будущий updateUser администратора принимает должность. User Service создаёт или обновляет employees и меняет роль одной транзакцией. В ЛР3 показано чтение уже созданного начального профиля, сам updateUser не исполняется.

**Почему не double для денег?** Дробные двоичные числа могут давать неточное округление. Сумма хранится long в копейках BYN.

**Почему GraphQL Long возвращается строкой?** Чтобы JSON-клиенты не потеряли точность 64-битного значения. Это явно описанное правило scalar.

**Что такое пагинация?** Получение части списка: page начинается с 0, size от 1 до 100. totalCount считает весь отфильтрованный список, hasNext показывает следующую страницу.

**Как считается загрузка?** Подтверждённые места всех выездов периода делятся на их суммарную вместимость. Для декабря 16/40=0.4. Это не среднее отдельных процентов.

**Почему аналитика требует начало суток UTC?** Популярность хранится по дням, поэтому нельзя точно посчитать часть дня. Период включает from и исключает to.

**Что такое N+1?** Когда для каждого элемента списка выполняется ещё один вызов. Платежи бронирований читаются одним пакетным вызовом по bookingIds через @BatchMapping.

**Готова ли система к реальному использованию?** Это базовая структура ЛР3. Есть чтение, тестовые токены и mock. Запись, настоящая авторизация, gRPC и Kafka относятся к следующим этапам.
